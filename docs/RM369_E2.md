## D4 contract

Orientation g = r + 4f, r in 0..3, f in 0..1.
Apply horizontal reflection first, then r clockwise quarter turns.
For A=(a,f), B=(b,h), A after B is
((a+(-1)^f*b) mod 4, f XOR h).
The inverse of a rotation negates its angle; all four reflections
are self-inverse. Composition is associative but noncommutative:
rotation 1 after reflection 4 is 5; reflection 4 after rotation 1 is 7.

There are two distinct operation concepts:
1. Physical slot local orientation edit: compose a gear with the
   selected node's current orientation, leaving all child addresses and
   their stored orientations untouched. This is E2's executable gear.
2. Active coordinate transform: map a coordinate into a rotated or
   reflected view. This is a pure function, not a state edit. Rotating
   the entire subtree would also permute descendant addresses and compose
   their orientations. That operation is deliberately not implemented.

E0's induction proof still applies to any edited local orientation.
An invariant is a validity property, not a proof of state identity.

## Program envelope

Input is an immutable canonical RM1 snapshot (E1). The program is a list
of [path, gear] pairs, where path is a list of physical child slot
integers. Empty path is root. Fuel is an integer 0..4096; each gear costs
one step, including identity. Insufficient fuel, malformed paths,
invalid gears or noncanonical snapshots raise ValueError. No successful
output is returned if a step fails. Execution uses a private decoded
copy, so the original bytes cannot be mutated.

The inverse program reverses instruction order and inverts each gear.
Applying it to the exact output restores the input byte for byte. It is
not a safe rollback after unrelated edits; callers must check the output
digest before using it. Receipts include the input/output digests,
ordered before/after states, remaining fuel, inverse program and
canonical SHA-256 receipt checksum. These checksums are not signatures,
authorization, or evidence of external execution.

Each local edit uses a sparse lookup and update, not a dense grid.
However, execution decodes the entire sparse snapshot and encodes/sorts
it again; receipt construction is linear in program length and path size.
Fuel measures steps only, not actual time or memory.
